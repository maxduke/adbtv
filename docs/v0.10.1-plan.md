# ADB TV 0.10.1 Stabilization Plan

Status: Automated candidate validated; physical validation pending.

## Release Intent

Improve the reliability and quality of the existing app before beginning App
Store submission work.

The published `0.10.0` release is the upgrade and regression baseline.
The candidate version is `0.10.1` build `18`.

## Confirmed Scope

- Make `0.10.1` a strict stabilization release.
- Keep the deployment baseline at iOS and iPadOS 17.
- Preserve Android 8 and Android 10 compatibility.
- Add no new product features.
- Perform a risk-based audit of every main app workflow rather than limiting
  review to recent changes or already reported defects.
- Give deeper scrutiny to connection lifecycle and ownership, cancellation,
  Managed Device changes, unreachable devices, and long-running ADB Operations.
- Fix confirmed defects and regressions in existing workflows.
- Apply targeted UI polish only where the audit finds clipping, inconsistent
  spacing, confusing states or actions, accessibility gaps, or weak loading and
  error presentation.
- Preserve the existing navigation model and visual direction; do not redesign
  the app in this release.
- Audit UI responsiveness during connection, refresh, transfer, installation,
  screenshot, shell, and file operations.
- Audit existing trust boundaries around APK, APKM, URL, archive, shell, and
  remote-file inputs; bounded command output; temporary-file cleanup; Device
  Credentials; and Diagnostic Detail.
- Fix concrete security or privacy defects at their source without adding
  speculative security layers or removing the intentional one-shot shell
  capability.
- Preserve user-initiated HTTP Install URLs for `0.10.1`. Verify the existing
  insecure-transport warning, HTTPS-to-HTTP redirect rejection, bounded
  download, and package validation.
- Defer changing `NSAllowsArbitraryLoads` and choosing HTTPS-only versus
  local-network HTTP behavior to the `0.11.0` App Store Submission Candidate,
  as required by ADR 0007.
- Check pinned production dependencies and bundled helper inputs for relevant
  advisories, license changes, and supported-platform compatibility.
- Change a dependency version only for a relevant security fix, confirmed
  defect, or required toolchain compatibility, with focused regression
  validation.
- Add no production telemetry, analytics backend, or crash-reporting SDK.
- Keep Diagnostic Detail local and user-controlled, adding missing context only
  when it materially improves troubleshooting without exposing secrets.
- Treat a blocked main thread, unavailable recovery, or missing cancellation
  from a stalled read-only operation as a defect. Preserve intentional
  concurrency locks around mutating operations where they prevent unsafe
  overlap.
- Optimize only when profiling or repeatable measurements identify a problem,
  and fix the root cause rather than adding speculative caching or concurrency.
- Preserve existing user-visible behavior unless a change is required for
  correctness, stability, accessibility, or clear UI quality.
- Block release for any reproducible crash, hang, wrong-device action, data
  loss, security defect, correctness failure, or serious accessibility issue.
- Include smaller UI and performance fixes only when they are contained,
  independently verifiable, and lower risk than deferral.
- Record larger non-blocking findings for a later release instead of expanding
  stabilization scope.
- Refactor only when a confirmed fix requires it for correctness, focused
  testability, or removal of duplication introduced by that fix. File size
  alone is not a stabilization defect.

## Out Of Scope

- New Android TV management capabilities.
- Production analytics or remote crash reporting.
- Navigation or visual redesign.
- Speculative performance work.
- App Store signing, submission, product-page metadata, and review preparation.
  Those belong to the planned `0.11.0` App Store Submission Candidate.
- Broad source-file splitting, architecture changes, and dependency refreshes
  without a confirmed release problem.

## Audit Areas

1. Device selection, pairing, connection, reconnect, reachability, Saved Device
   recovery, Device Credential handling, and operation ownership.
2. Remote Session responsiveness, repeated actions, media controls, text input,
   scene changes, disconnects, and action failure recovery.
3. Installed Apps, Active Apps, helper metadata, App Details, launch, Force
   Stop, guarded Preinstalled App controls, refresh, and stale-result handling.
4. Single APK and APKM installation from Files and URL, validation, progress,
   cancellation, package-manager sessions, and local and remote cleanup.
5. Device Information, storage cleanup, TV Screenshot, One-shot Shell Command,
   built-in commands, and remote file browsing, transfer, and deletion.
6. Clean install, `0.10.0` upgrade, persisted settings, helper-state
   compatibility, first-run permissions, backgrounding, and cold launch.
7. Loading, empty, success, disabled, cancellation, and error states; compact
   and regular-width layout; dark mode; Dynamic Type; VoiceOver; and contrast.
8. Input validation, output and allocation bounds, archive and path safety,
   temporary data, secrets, Diagnostic Detail, dependency advisories, and legal
   notices.
9. Main-thread responsiveness and measured resource behavior during connection,
   parsing, transfers, installation, screenshot capture, and app-list loading.
10. Clean-checkout build, required CI, unsigned packaging, checksum, embedded
    version and legal resources, README accuracy, and release notes.

## Audit Method

1. Use tagged `v0.10.0` behavior and existing tests as the baseline.
2. Review shared connection, session, operation, timeout, and state-ownership
   paths before individual screens so one root-cause fix covers every caller.
3. Run the current automated checks before changing behavior and record only
   reproducible findings with evidence.
4. Exercise the representative interruption, upgrade, helper, accessibility,
   and physical-device matrices defined below.
5. Rank findings by release risk. Accept only blocking fixes and contained
   lower-risk corrections into the implementation scope.
6. For each accepted finding, identify its root cause, smallest safe change,
   focused regression check, and affected physical checks before editing code.
7. Keep App Store observations in a separate `0.11.0` input list.

## Validation

- Add the smallest focused regression test for every nontrivial logic or
  state-management fix that can be exercised deterministically.
- Reuse existing test suites, fixtures, and UI snapshot slots; do not pursue an
  arbitrary coverage percentage or broadly rewrite old tests.
- Use snapshot validation for visual fixes when appearance is the behavior
  being protected.
- Run the full workflow regression on the primary Android 10 TV.
- On Android 8, run protocol-sensitive and compatibility-critical workflows
  rather than duplicating every presentation-only check.
- Use physical iPhone hardware for permissions, Files integration, sharing,
  camera pairing, app lifecycle, and responsiveness.
- Use iPhone and iPad simulators for compact, regular-width, dark-mode, and
  accessibility layouts.
- On critical workflows, verify large Dynamic Type, VoiceOver names, values,
  states and actions, logical focus order, sufficient contrast, and status cues
  that do not rely on color alone.
- Cover device selection, remote control, app management, tools, installation,
  and error recovery in the critical accessibility pass.
- Validate both a clean install and an upgrade from `0.10.0`.
- During upgrade validation, retain Saved Devices, Device Credentials,
  preferences, and existing Android helper state; verify that stale state does
  not bypass reachability checks or trap navigation.
- Validate helper-free behavior, the bundled helper, an upgradeable older
  helper, and a signature-incompatible helper installation.
- Keep core ADB workflows available without the helper. Verify clear recovery
  guidance when Android requires removal of an incompatible helper signature.
- Exercise representative read, transfer, and mutation workflows under device
  disconnect, cancellation, app backgrounding, navigation away, and Managed
  Device changes where navigation is allowed.
- Require bounded recovery, rejection of late results, retention of correct
  device ownership, and cleanup of temporary local and remote artifacts.
- Do not test every operation/interruption combination when one representative
  path protects the same shared implementation.
- Reuse the current required SwiftPM, iOS simulator, and Android helper checks
  for reviewable changes.
- Run the existing visual snapshot and unsigned-IPA packaging validations once
  against the final candidate.
- Add no permanent high-cost CI job unless a concrete defect demonstrates that
  the current checks cannot protect the affected behavior.

## Delivery

- Publish `0.10.1` through the existing unsigned GitHub release process.
- Do not add App Store signing, TestFlight upload, or a second distribution
  pipeline in this release.
- Perform the audit before selecting implementation work.
- Deliver accepted fixes in one focused pull request with small commits grouped
  by root cause or workflow.
- Run targeted checks while developing each fix, then run the full automated,
  visual, packaging, and physical matrix against the coherent release
  candidate.
- After a candidate correction, repeat affected gates and the final smoke test
  rather than rerunning unrelated expensive checks.
- Record App Store compliance findings encountered during stabilization in a
  separate prioritized input list for `0.11.0`; do not implement them
  opportunistically in `0.10.1`.

## Release Gates

- No accepted release-blocking finding remains unresolved.
- Existing required CI passes from a clean checkout with no new warning caused
  by the release.
- Every accepted nontrivial fix has focused regression coverage.
- The final visual snapshots and unsigned IPA packaging checks pass.
- The downloaded IPA checksum, ZIP structure, bundle identifier, version
  `0.10.1`, build `18`, helper APK, icon assets, license, and third-party notices
  are verified.
- The risk-based physical matrix passes on the primary Android 10 TV, the
  Android 8 compatibility target, and physical iPhone hardware.
- Upgrade from published `0.10.0` and clean install both pass.
- README, hardware checklist, release notes, and Diagnostic Detail describe the
  final behavior accurately.

## Done Means

- `0.10.1` changes only confirmed defects and contained quality gaps; it adds no
  product feature or broad refactor.
- Core workflows recover cleanly from unreachable devices, cancellation,
  backgrounding, stale results, and allowed device changes without freezing the
  UI or acting on the wrong Managed Device.
- Transfers and installations clean up temporary local and remote artifacts on
  success, failure, and cancellation where the transport permits cleanup.
- Critical workflows remain usable without the optional helper and accessible
  with large Dynamic Type and VoiceOver.
- Performance changes are supported by repeatable before-and-after evidence.
- The unsigned GitHub release can be installed from a clean checkout using the
  documented process.
- App Store findings are preserved for `0.11.0` without expanding this release.

## Audit Record

Audit date: 2026-07-30.

Accepted findings:

1. File uploads wrote directly to the destination. An interrupted replacement
   could truncate an existing file. Uploads now stage to a hidden sibling and
   replace the destination only after ADB Sync completes.
2. The basic ADB Sync response decoder trusted a device-provided failure length
   and could buffer an unreasonable response. Failure messages now use the same
   64 KiB bound as the directory and pull decoders.
3. Legacy shell sessions had a per-packet bound but no total-output bound.
   Accumulation now stops at 16 MiB; user-facing one-shot shell remains bounded
   more tightly at 256 KiB.
4. APK staging could carry stale document-picker size metadata into the install
   plan after independently copying and measuring the file. The install plan
   now uses the staged file's verified size.

No-change conclusions:

- Connection ownership, Saved Device verification, Remote Session recovery,
  cancellation, stale-result rejection, and scene lifecycle paths showed no
  reproducible release defect.
- APKM path validation, bounded extraction, URL scheme and redirect checks,
  local staging cleanup, package-session abandonment, and APK remote cleanup
  remain appropriate.
- BoringSSL SwiftPM `0.41.0` and ZIPFoundation `0.9.20` are the newest
  repository tags inspected, with no repository security advisories reported.
- The existing 88-image iPhone/iPad, light/dark, regular/accessibility snapshot
  artifact showed no blocking overlap, clipping, or contrast defect.
- Packaging already validates the icon, helper APK, permission descriptions,
  imported APK type, legal notices, built version, and release tag agreement.

App Store-specific findings are recorded separately in
[v0.11.0 App Store Inputs](./v0.11.0-app-store-inputs.md).
