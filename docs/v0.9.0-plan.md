# ADB TV 0.9.0 Plan

Status: Planning

## Release Intent

Let a user disable an unwanted Preinstalled App that consumes resources and
later restore it. Keep the workflow within the existing Apps area.

`0.9.0` remains one cohesive feature release rather than a collection of
unrelated tools or broad maintenance work.

## Scope Boundary

- Manage complete Preinstalled App packages.
- Preserve disabled packages so the user can enable them again.
- Let the user choose packages; do not estimate resource consumption or
  recommend packages to disable.
- Do not expose Android receiver, service, provider, or activity component
  controls.
- Do not claim that ADB TV can determine whether every OEM package is safe to
  disable.

## Eligibility Policy

- Show all Preinstalled Apps.
- Prevent disabling packages that ADB TV identifies as Android framework,
  System UI, the active launcher, Settings, package installer, the active
  input method, or ADB TV Helper.
- Protect reviewed ecosystem infrastructure identifiers, including Google Play
  services, Google Services Framework, Play Store, and known OEM equivalents.
- Treat the reviewed identifier set as an additional guardrail rather than an
  exhaustive cross-OEM catalog.
- Explain why the disable action is unavailable for a Protected Preinstalled
  App.
- Warn before disabling every other Preinstalled App.
- Treat protection as a guardrail. An unprotected package is not certified
  safe because OEM dependencies vary by device and firmware.
- If any required protection check cannot identify its package, fail closed:
  disable every new Disable action and explain that safety checks are
  incomplete.
- Keep browsing, existing app-management actions, and Enable recovery
  available when protection checks are incomplete.

## Recovery

- Keep Disabled Preinstalled Apps in the existing System Apps list.
- Mark their state clearly and keep them discoverable through app search.
- Establish the Managed Disablement before sending the Disable operation, then
  present the package as disabled only after Android reports that state.
- Offer Enable only when Android reports the package disabled and it has a
  Managed Disablement for that Managed Device.
- Keep packages disabled by Android, the OEM, or another tool visible, but do
  not offer to enable them.
- Remove the Managed Disablement only after Android reports and ADB TV verifies
  that the package returned to its default state.
- Refresh the app's state after either action so the UI reflects the device
  rather than assuming the command succeeded.
- When deleting a Saved Device with Managed Disablements, require confirmation
  and offer Review Disabled Apps before removal.
- Review Disabled Apps opens the existing System Apps list filtered to that
  device's Managed Disablements.
- Restore each package separately through the normal Enable action; do not add
  an Enable All operation.
- Keep Remove Anyway available for an unreachable TV, with an explicit warning
  that ADB TV will lose its recovery records.
- Never discard Managed Disablements through an unconfirmed device deletion.

## Confirmation

- Require a destructive confirmation before disabling an eligible
  Preinstalled App.
- Show its display name and package identifier.
- Warn that ADB TV cannot know every OEM dependency and that disabling the app
  may remove TV features or affect other apps.
- Explain that the package remains installed and can be enabled again from the
  same System Apps entry.
- Enabling an app does not require destructive confirmation.

## Presentation

- Keep disable and enable controls in the Preinstalled App detail screen.
- Add one compact System Control section containing the package state,
  protection or recovery explanation, and the available action.
- Mark disabled packages in System Apps rows so their state remains scannable.
- Do not add disable actions to list rows, swipe actions, or context menus.
- Reuse the existing app-detail layout and destructive confirmation style.

## Operation Model

- Disable or enable one Preinstalled App at a time.
- Apply the change only to the active Android user and do not expose a user
  selector.
- Resolve and retain the numeric Android user ID so recovery cannot affect a
  different profile if the TV's active user later changes.
- Disable additional app actions while the package state change is running.
- Verify the package's reported state after the command completes.
- Do not add selection mode, batch operations, or partial-batch recovery.

## Persistence

- Store Managed Disablements with their Saved Device in the existing local
  Device Library.
- Preserve them across app restarts, device renames, and connection updates.
- Decode existing Saved Devices without this new data as having no Managed
  Disablements.
- Persist recovery authority before sending the disable command. Refuse to
  disable the package if that save fails.
- Reconcile the durable record with Android's reported package state after the
  operation and whenever System Apps reload.
- Remove a stale record when Android reports the package enabled.
- Keep the record when the remote outcome is disabled or cannot be determined,
  so recovery remains available.
- Do not add helper storage or cloud synchronization.

## Failure Behavior

- Treat Android's queried package state as authoritative when it can be read,
  even if the preceding command returned an unusual result.
- When the resulting state cannot be verified, show State Not Confirmed and do
  not claim success.
- Retain recovery authority after an unconfirmed Disable outcome.
- Provide Check Again instead of automatic retries.
- Keep the existing User Error and expandable Diagnostic Detail presentation.
- Reconcile state after cancellation, timeout, disconnect, app interruption,
  or the next System Apps reload.

## Decisions Pending

- How enabled and disabled states are loaded.
- Android-version and OEM compatibility boundaries.
- Automated and physical validation requirements.
