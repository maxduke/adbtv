# ADB TV 0.9.0 Plan

Status: Implemented; physical validation and release packaging pending

## Release Intent

Add one focused workflow for disabling an unwanted Preinstalled App and
restoring Android's default package state later. Keep it inside the existing
Apps area.

## Scope

- Manage complete Preinstalled App packages for the active Android user.
- Show effective enabled or disabled state in the existing System Apps list.
- Let the user choose packages; do not estimate resource use or recommend
  packages to disable.
- Preserve package data.
- Do not expose receiver, service, provider, or activity component controls.
- Do not claim that ADB TV can determine whether every OEM package is safe to
  disable.

## Workflow

- Mark effectively disabled packages in System Apps rows.
- Add one compact System Control section to the existing app-detail sheet.
- For an eligible enabled package, show Disable.
- For a Protected Preinstalled App, show its protection reason.
- For any effectively disabled package, show Restore Android Default.
- Keep these actions out of list menus and swipe actions.
- Disable Launch and Force Stop while a package is effectively disabled.
- Run one package-state operation at a time.

Before Disable, require a destructive confirmation showing the display name,
package identifier, and a warning that TV features or other apps may stop
working.

Before Restore Android Default, explain that ADB TV will remove the per-user
override. Android may activate a package previously disabled by the OEM, the
user, or another tool.

## Safety Boundary

- Maintain a small reviewed denylist for packages whose disablement would
  predictably compromise Android, ADB management, or protected ecosystem
  infrastructure.
- Protect the active launcher, Settings app, and active input method identified
  by native Android queries.
- If a required active-role query fails or returns malformed data, hide every
  new Disable action and explain that safety checks are unavailable.
- Keep Restore Android Default available because it removes an override rather
  than creating one.
- Warn before disabling every other Preinstalled App.
- Treat all protection as a guardrail. An unprotected package is not certified
  safe across OEM devices and firmware.

Do not build a broad OEM package catalog. Add an identifier only when its role
is understood and supported by documentation or physical validation.

## Native Android Operations

- Resolve the active numeric user with `am get-current-user`.
- Load Preinstalled Apps with
  `pm list packages -s --user <user-id>`.
- Load their effective disabled state with
  `pm list packages -s -d --user <user-id>`.
- Resolve active protected roles with bounded, validated package-manager and
  settings queries.
- Disable with
  `pm disable-user --user <user-id> <package>`.
- Restore with
  `pm default-state --user <user-id> <package>`.
- Query effective disabled state after either action before reporting success.

Use `default-state` instead of `enable`: restoration removes the per-user
override and respects the package's Android default. If Android still reports
the package disabled afterward, explain that Android keeps it disabled by
default.

Package state and controls use native shell commands. Optional helper metadata
remains a separate best-effort source for names, versions, sizes, and icons.

## Failure Behavior

- Treat the queried Android package state as authoritative.
- Use the existing User Error and expandable Diagnostic Detail presentation.
- Use the existing Refresh Apps action after cancellation, timeout, disconnect,
  malformed output, or an unverified result.
- Keep browsing and restoration available when safety checks prevent new
  disablements.
- Do not add automatic retries, a second recovery state machine, or background
  monitoring.

## Implementation

1. Extend `ADBTVInstalledAppManager` with active-user parsing, system package
   state loading, protected-role loading, Disable, and Restore Android Default.
2. Extend the existing installed-app view state and command flow with effective
   disabled state and protection reasons.
3. Add the System Control section, confirmations, disabled row status, and
   existing-operation progress messages to `ADBTVRootView`.
4. Update focused tests, hardware validation, and user documentation.

Do not change `ADBTVDeviceSummary`, Device Library persistence, device deletion,
Android Helper, navigation structure, or production dependencies.

## Compatibility

- Keep Android 8.0 (API 26) as the compatibility floor.
- Use numeric user IDs because Android 8's legacy
  `pm disable-user --user` parser does not accept `current`.
- Treat rejected shell permission, missing role resolution, malformed output,
  and OEM command divergence as unavailable safety checks.
- Require no Android Helper installation.
- Make no claim below Android 8 or for vendor-modified package managers without
  physical evidence.

## Automated Validation

- Validate bounded active-user, package-list, disabled-list, and protected-role
  output.
- Reject malformed user IDs, package identifiers, components, duplicates, and
  shell metacharacters.
- Verify exact numeric user scoping for `disable-user` and `default-state`.
- Cover enabled, disabled, protected, and unavailable-safety presentation
  states.
- Cover checked command failure and post-command state mismatch.
- Run the existing Swift package CI, iOS build, and representative UI snapshot
  checks.

## Physical Validation

- On Android 8.0 and Android 10.0 hardware, disable one known non-critical
  Preinstalled App, confirm it cannot launch, and verify its data remains.
- Reboot the TV and confirm Android retains the disabled state.
- Restore Android Default and verify the effective state is refreshed.
- Verify the active launcher, Settings, input method, and reviewed critical
  packages cannot be disabled.
- Verify an OEM-disabled package displays Restore Android Default with the
  explicit warning.
- Repeat state loading and both actions without Android Helper installed.
- Disconnect or cancel during an action, reconnect, refresh, and confirm the UI
  follows the TV's actual state.

## Out of Scope

- Component-level service or receiver controls.
- Resource profiling or disable recommendations.
- Batch operations.
- Package-state history or ownership tracking.
- Device Library recovery records.
- Cloud synchronization.
- New helper capabilities.
