# ADB TV 0.10.0 Plan

Status: Release candidate; physical output and latency measurements remain
release gates.

## Release Intent

Help the user identify apps that are active on an Android TV and inspect their
current memory footprint without turning ADB TV into a continuous process
monitor or making automated resource-management recommendations.

## Confirmed Scope

- Add a third **Active** segment beside **User** and **System**. Keep the short
  visible labels for compact and accessibility layouts, with full accessibility
  labels for **User Apps** and **System Apps**.
- Load an App Activity Snapshot when Active is opened and on manual refresh.
- Show when the snapshot was last updated; do not poll in the background.
- Keep the presentation as a compact searchable list with no summary dashboard.
- Keep the app name and package identifier visible, add one compact status line
  for foreground, User or System, and process count, and show formatted memory
  at the trailing edge without compressing long identifiers.
- Include Installed Apps with at least one live process at refresh time.
- Group multiple processes belonging to one package into one Active App.
- Identify every confidently resolved foreground app.
- Show total proportional set size (PSS) and process count for each Active App.
- Put foreground apps first, then sort remaining apps by PSS descending.
- Mark each Active App as User or System.
- Keep the existing app search, App Details, Launch, and Force Stop workflows.
- Add a compact Activity section to App Details using the selected snapshot:
  Foreground or Background, Memory, Process Count, and Updated time.
- Preserve the existing System Control section and safety checks when an Active
  System App opens App Details.
- In Active, treat the native live-process snapshot as authoritative for
  whether Force Stop is available; optional helper `stopped` metadata cannot
  disable the action.
- Refresh Active after a successful app action.
- After Force Stop, show the refreshed Android state. If Android restarts or
  retains the app, keep it listed and explain that result instead of claiming
  the app stopped or treating the accepted command as a transport failure.
- Keep the last successful snapshot visible during refresh.
- If refresh fails, retain the previous rows and their update time while
  presenting the failure.
- Cancel collection when the user leaves Active or changes Managed Device, and
  discard every late result from the cancelled operation.
- Treat Active refresh as a cancellable read-only operation: keep tool, back, and
  device navigation available by cancelling refresh before leaving, while all
  mutating app operations retain the existing navigation lock.
- Cancel Active refresh when the app leaves the active scene.
- Require no Android helper for activity or memory data.
- Show package identifiers and generic icons as soon as the native snapshot is
  ready, then reuse the existing non-blocking helper loader for optional names
  and icons for only the Active Apps.
- Include only processes that can be confidently attributed to one Installed
  App.
- Exclude ordinary unassociated core daemons without warning.
- If a process appears associated with an Installed App but fails UID or
  ownership validation, omit it and report the partial-data count in
  Diagnostic Detail.
- Keep confidently identified apps when foreground or memory data is
  unavailable.
- Show **Unavailable** for missing memory, sort those rows after known PSS
  values and alphabetically among themselves, and show one partial-snapshot
  warning with Diagnostic Detail.

## Safety And Failure Behavior

- Treat every snapshot as point-in-time data, not a claim that an app remains
  active after refresh.
- Do not label an app safe to stop, disable, or remove based on resource data.
- Preserve the stronger confirmation already required before Force Stop on a
  Preinstalled App.
- Keep collection bounded by timeout, cancellation, and output-size limits.
- Reuse the existing 30-second Installed Apps hard timeout and require normal
  refresh to finish within 10 seconds on both physical compatibility targets.
- Bind collection and actions to the selected Managed Device through the
  existing device-operation ownership rules.
- Require helper-free physical validation on Android 8.0 and Android 10.0
  before release.

## Out Of Scope

- Continuous monitoring, charts, alerts, or activity history.
- CPU, network, battery, storage, or app-data measurements.
- Raw process and PID management.
- Shared-UID attribution heuristics.
- Automated cleanup or resource recommendations.
- Batch Force Stop or package-state actions.
- New Android helper capabilities.
- Component-level service, receiver, provider, or activity controls.

## Release Discipline

- Keep App Activity Snapshot as the only new workflow.
- Allow repo-wide opportunistic polish only for a confirmed low-risk bug,
  accessibility gap, or small UI correction found during implementation or
  validation.
- Give every opportunistic fix focused validation and a separate reviewable
  commit.
- Defer any polish that requires a new production dependency, workflow,
  architecture decision, domain concept, or expanded hardware matrix.
- Do not use this release for broad refactoring or redesign.

## Native Android Operations

- Resolve the active numeric Android user with `am get-current-user` before
  collection.
- Refresh both package inventories with
  `pm list packages -3 -U --user <id>` and
  `pm list packages -s -U --user <id>`. Parse only
  `package:<name> uid:<uid>` rows.
- Run one bounded `ps -A -w -o PID,UID,NAME` command and use its numeric UID to
  keep only processes belonging to that Android user.
- Run one bounded `dumpsys meminfo -c` command per refresh.
- Require compact-format version `1`, declared by both target AOSP releases,
  before accepting process rows.
- Parse only validated `proc` rows containing process name, PID, and nonnegative
  PSS in KiB. Convert to bytes with checked `Int64` arithmetic for display.
- Never double-count duplicate process or memory identities. Omit the ambiguous
  process or its memory value and report a partial snapshot.
- Join memory rows to active-user process rows only when both validated PID and
  exact process name match, preventing process churn or PID reuse from
  attributing stale memory.
- Attribute an active-user process only when its name exactly matches an
  Installed App package or uses that package followed by Android's `:`
  child-process suffix.
- Require the process UID to match the package UID and exclude packages whose
  UID is shared by more than one Installed App.
- Sum PSS and process count for all confidently attributed processes belonging
  to one package.
- Keep an Active App with unavailable memory when its process attribution is
  valid but no valid PSS row exists.
- Resolve resumed apps from exact `mResumedActivity:` and `ResumedActivity:`
  records in one bounded `dumpsys activity activities` query, deduplicating the
  same component when Android emits both forms.
- Mark a resumed package Foreground only when that package is also confidently
  present in the active-process snapshot; otherwise report snapshot churn in
  Diagnostic Detail without inventing an Active App.
- Recheck the active numeric Android user after collection and discard the
  entire result if the user changed.
- Do not run one memory command per package.
- Execute each snapshot command through the existing checked-shell marker and
  `ADBDeviceToolsSession.runService` streaming cap, not the unbounded
  `runShellCommand` helper.
- Start with the existing 256 KiB package-list limit, 1 MiB for process output,
  and 2 MiB each for compact memory and activity output. Record actual byte
  counts on Android 8 and Android 10; increase a cap only when a measured valid
  target exceeds it.
- Give `runService` a small fixed allowance for the checked-shell exit marker,
  then post-validate the command payload against its stated cap, matching the
  existing bounded Device Tools pattern.
- Parse and release each raw command output before collecting the next large
  output so the snapshot does not retain all raw responses in memory.
- Do not add `--local` to compact aggregate meminfo: AOSP accepts the option, but
  its process-local behavior applies to detailed process collection, which this
  aggregate compact request does not perform.

## Implementation

1. Extend `ADBTVInstalledAppManager` with App Activity Snapshot package-UID,
   process, compact-memory, resumed-activity parsing, and aggregation. Reuse
   `ADBDeviceToolsSession` for bounded checked commands; add no session protocol.
2. Add focused parser and aggregation tests before connecting the snapshot to
   the app.
3. Add a private Apps presentation mode for User, System, and Active. Keep
   `ADBTVInstalledAppScope` unchanged because it represents package origin, not a
   view.
4. Keep a separate device-bound activity snapshot in the existing Installed
   Apps state so switching modes, refreshing, cancellation, and failures do not
   erase the last successful Active rows.
5. Extend the existing Installed Apps command, result, cancellation, 30-second
   timeout, operation-ID late-result guard, and device-ownership flow without
   adding another operation coordinator. Make only Active refresh release its
   navigation lock through cancellation.
6. Load the existing `ADBTVSystemAppSnapshot` only when an Active System App
   opens App Details. Show Activity immediately and let System Control load
   independently rather than running protection-role queries on every refresh.
7. Reuse the existing asynchronous helper metadata loader only for the current
   Active packages. Keep helper metadata separate from snapshot-authoritative
   Force Stop availability.
8. Add the Active segment, compact rows, partial-data presentation, and
   snapshot-backed Activity section to the existing Apps and App Details views.
   Use an accessibility layout that places memory below the identifier when a
   trailing metric would compress content.
9. Retarget the existing Apps and App Details UI snapshot slots to Active and
   Activity details. Do not add simulator launches: recent runs already take
   about 15 to 20 minutes against a 20-minute job timeout.
10. Update the hardware checklist and README, set version
   `0.10.0` build `17`, and package a release candidate for physical validation.

## Validation

- Add parser fixtures representative of Android 8 and Android 10 package,
  process, compact-memory, and resumed-activity output.
- Cover compact-format version rejection, malformed or duplicate PIDs,
  negative and overflowing numeric values, long output, wrong-user processes,
  shared UIDs, package-prefix collisions, valid `package:child` processes,
  partial PSS, multiple foreground apps, and active-user changes.
- Cover deterministic grouping, total PSS, process count, ordering, search,
  unavailable-memory ordering, partial diagnostics, and late-result rejection.
- Cover PID reuse by rejecting a meminfo row whose PID matches but process name
  does not, duplicate resumed-activity forms, and multiple distinct resumed
  packages.
- Reuse existing Installed Apps operation ownership, cancellation, timeout,
  App Details, System Control, Launch, and Force Stop tests.
- In the existing iPhone and iPad light, dark, and accessibility snapshot slots,
  capture the compact Active list and an Active system-app detail containing
  both Activity and System Control.
- On Android 8.0 and Android 10.0 without the helper, validate package
  classification, foreground state, PSS, process count, refresh, cancellation,
  the 10-second normal-latency target, and user-app Force Stop.
- Record output byte counts and elapsed refresh time for each physical target.
  Verify every output stays below its cap with headroom; do not infer this from
  fixtures or AOSP source.
- While Active refresh is deliberately delayed or the TV becomes unreachable,
  verify Cancel, User/System segment changes, tool changes, back navigation,
  device selection, scene backgrounding, and immediate retry all discard the
  old result without unlocking mutating operations.
- On either physical TV, validate non-blocking helper names and icons plus one
  disposable System App action with the existing stronger confirmation.

## Done Means

- A clean checkout passes SwiftPM tests, the iOS simulator build, Android helper
  regression checks, and release-candidate packaging.
- The Active list and Activity details remain usable on iPhone and iPad in
  light, dark, and accessibility layouts without clipped identifiers or
  metrics.
- Android 8.0 and Android 10.0 pass the helper-free physical matrix within the
  agreed normal-latency and measured output-cap targets.
- No snapshot, process data, memory data, or activity history is persisted.
- README, glossary, release plan, and hardware checklist match the shipped
  behavior.
